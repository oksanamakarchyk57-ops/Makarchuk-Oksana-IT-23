# Лабораторна / Практична робота №1

## 1. Обґрунтування обраних типів даних (Завдання 5)

Для створення таблиці-виміру №1 було обрано такі типи даних SQLite з урахуванням концепції **Type Affinity**:

* **`id` (`INTEGER PRIMARY KEY AUTOINCREMENT`)**:
  Використовується для унікальної ідентифікації кожного запису (первинний ключ). Тип `INTEGER` у поєднанні з `PRIMARY KEY` робить цей стовпець псевдонімом внутрішнього `ROWID`, що забезпечує автоматичну генерацію унікальних цілочисельних ідентифікаторів та швидкий пошук.

* **`name` / `title` (`TEXT`)**:
  Використовується для збереження текстової інформації (назви, імена, описи). Тип `TEXT` підтримує довільні рядки у кодуванні UTF-8 та не обмежує довжину жорстко, що зручно для збереження довільного тексту.

* **`price` / `amount` (`REAL` або `NUMERIC`)**:
  Обрано для збереження дробових продуктів чи грошових значень (ціна, вага тощо). `REAL` зберігає значення як 8-байтові числа з плаваючою крапкою IEEE, що є оптимальним для дробових величин.

* **`created_at` (`TEXT`)**:
  Для збереження дат та часу в SQLite використовується текстовий формат `ISO8601` (`YYYY-MM-DD HH:MM:SS`), оскільки в SQLite немає окремого вбудованого типу `DATETIME`. Тип `TEXT` дозволяє легко сортувати та порівнювати дати за допомогою вбудованих функцій дати та часу.

* **`is_active` (`INTEGER`)**:
  Використовується як булевий прапорець (`0` — хибність, `1` — істина), оскільки в SQLite відсутній окремий тип `BOOLEAN`.

## 2. Відповіді на контрольні питання

### 1. Чому SQLite називають файловою, безсерверною СУБД — і що саме це означає на практиці для файлу `lab_work_1.db`?
* **Безсерверна (Serverless):** На відміну від СУБД на кшталт PostgreSQL чи MySQL, SQLite не потребує окремого фонового процесу-сервера, який потрібно запускати, налаштовувати чи адмініструвати. Запити виконуються безпосередньо бібліотекою SQLite, вбудованою в застосунок чи CLI-клієнт.
* **Файлова (File-based):** Вся база даних (схема, таблиці, індекси, дані) зберігається в одному-єдиному бінарному файлі на диску — у нашому випадку `lab_work_1.db`.
* **На практиці:** Файл `lab_work_1.db` можна легко скопіювати, перейменувати, перенести на інший комп'ютер чи надіслати викладачеві разом із проєктом. Для роботи з ним не потрібно розгортати локальний сервер СУБД.

### 2. Яка різниця між роботою через `sqlite3` (CLI) і через `DB Browser for SQLite` — коли зручніший кожен із них?
* **`sqlite3` (Command Line Interface):**
  * **Особливості:** Інтерфейс командного рядка. Робота відбувається за допомогою системних крапкових команд (наприклад, `.tables`, `.schema`, `.open`) та стандартних SQL-запитів.
  * **Коли зручний:** Для швидкого виконання скриптів (`.read script.sql`), автоматизації дій у консолі, роботи на серверах без графічного інтерфейсу та глибокого розуміння команд SQL.
* **`DB Browser for SQLite` (GUI):**
  * **Особливості:** Графічний застосунок з візуальним відображенням таблиць, зручним редагуванням комірок, візуальним майстром створення схем та можливістю експорту/імпорту.
  * **Коли зручний:** Для наочного перегляду даних, візуального аналізу структури, швидкої правки окремих записів без написання `UPDATE`-запитів та для початкового знайомства з базою даних.

### 3. Що таке type affinity в SQLite і чим це принципово відрізняється від типізації стовпців у PostgreSQL?
* **Type Affinity (Спорідненість типів) в SQLite:**
  SQLite використовує **динамічну типізацію**. Тип даних прив'язується не до стовпця, а до самого значення (комірки). Оголошений тип стовпця виражає лише його *спорідненість* (рекомендований тип: `INTEGER`, `TEXT`, `BLOB`, `REAL`, `NUMERIC`). При вставці SQLite намагається привести значення до спорідненого типу стовпця, але якщо це неможливо — збереже значення у його оригінальному типі (наприклад, текстовий рядок у стовпці `INTEGER`).
* **Відмінність від PostgreSQL:**
  PostgreSQL реалізує **жорстку (статичну) типізацію**. Тип даних закріплюється за стовпцем під час створення таблиці. Якщо спробувати вставити несумісний тип даних (наприклад, рядок "abc" у стовпець `INTEGER`), PostgreSQL видасть помилку виконання і скасує транзакцію.

### 4. Чим стовпець `id INTEGER PRIMARY KEY` відрізняється поведінкою від звичайного стовпця типу `INTEGER`?
1. **Псевдонім для ROWID:** Стовпець, оголошений саме як `INTEGER PRIMARY KEY` (з точним дотриманням синтаксису), стає прямим псевдонімом для внутрішнього 64-бітного цілого числа `ROWID`, яке SQLite використовує для унікальної ідентифікації рядків у B-Tree.
2. **Автоінкремент:** Якщо при вставці нових даних (`INSERT`) не вказувати значення для `INTEGER PRIMARY KEY` або передати `NULL`, SQLite автоматично згенерує наступне унікальне ціле число (більше за максимальне наявне). Звичайний стовпець `INTEGER` без `PRIMARY KEY` у такому випадку просто збереже `NULL`.
3. **Швидкість доступу:** Пошук за `INTEGER PRIMARY KEY` відбувається максимально швидко (за $O(1)$ або $O(\log N)$), оскільки запити звертаються безпосередньо до первинного індексу таблиці.
