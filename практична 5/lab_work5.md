1. Перебудова таблиці routes з обмеженнями

SQLite не вміє додавати обмеження до вже створеної таблиці командою ALTER TABLE, тому використано стандартний шлях перебудови:

Вимкнено перевірку зовнішніх ключів (PRAGMA foreign_keys = OFF), щоб видалення старої таблиці не заблокувалось зв'язками з trips.
Створено нову таблицю routes_new з потрібними обмеженнями.
Дані перенесено з routes у routes_new, стару таблицю видалено, нову перейменовано на routes.
Перевірку зовнішніх ключів знову ввімкнено (PRAGMA foreign_keys = ON).
Командою PRAGMA foreign_key_check підтверджено, що після перебудови зв'язки з таблицею trips не порушені (результат порожній).

У новій таблиці задано такі обмеження:

CHECK для distance_km: значення має бути більшим за 0 і не більшим за 10000 км, бо відстань маршруту не може бути від'ємною чи нульовою, а значення понад 10000 км для рейсів компанії нереалістичне;
UNIQUE для пари (origin, destination): один і той самий маршрут не повинен повторюватись у довіднику;
NOT NULL для origin і destination: маршрут без пункту відправлення чи призначення не має змісту;
DEFAULT для origin: якщо пункт відправлення не вказано, підставляється «Київ» як основний хаб компанії.

2. Перевірка CHECK

Зроблено спробу вставити маршрут із від'ємною відстанню (-5 км). SQLite відхилив вставку з повідомленням:

CHECK constraint failed: distance_km > 0 AND distance_km <= 10000

Рядок у таблицю не потрапив. Це підтверджує, що обмеження діє.

3. Перевірка UNIQUE

Зроблено спробу вставити маршрут Київ–Львів, який уже є в таблиці. SQLite відхилив вставку з повідомленням (вставте дослівно те, що показав ваш клієнт):

UNIQUE constraint failed: routes.origin, routes.destination

4. Перевірка DEFAULT

Вставлено маршрут без вказання origin. Перевірка вибіркою показала, що в колонці origin автоматично з'явилось значення «Київ». Тестовий рядок після перевірки видалено, щоб не засмічувати довідник.

5. Перевірка NOT NULL

Зроблено спробу вставити в trips рейс без дати (trip_date не вказано). SQLite відхилив вставку з повідомленням (вставте дослівно):

NOT NULL constraint failed: trips.trip_date

6. Висновок

Усі обмеження спрацювали: некоректні дані (від'ємна відстань, дубль маршруту, рейс без дати) база відхилила, а пропущену необов'язкову колонку заповнила значенням за замовчуванням. Перевага такого підходу в тому, що коректність даних гарантує сама база, а не лише програма чи користувач, який із нею працює. Перебудова таблиці не порушила зв'язків: дані та зовнішні ключі trips залишились цілими.
